## 1. 起点：从「本机 DSH」到「手机版 DSH」，再到「烫得受不了」

**来龙去脉**（这是项目的真实起点）：

1. 一开始我在**笔记本上本地构建 DSH**（DeepSeek Harness）。能用，但很不方便 —— DSH 是跑在本机的服务，总不能一直坐在电脑前问问题。
2. 于是我用 **DeepSeek 网页端**去找手机版，找到了 [**woaiys3/deepseek-harness-android-app**](https://github.com/woaiys3/deepseek-harness-android-app)：一位大佬把 DSH 打包成了可以直接安装的 Android APK。
3. 装上之后确实方便了，但有个很严重的毛病：**发热极其严重** —— 用十几分钟就明显烫手，电量掉得也快。
4. 所以我用 **WorkBuddy 国际版**的免费模型额度（底层是 DeepSeek-V4.1-Flash）接入模型，自己写了一个原生 Android 客户端（CoolStream），目标只有一个：把发热降下来。
5. 顺带一个插曲：写 CoolStream 期间 GitHub 一直连不稳，最后是靠**笔记本上那份 DSH** 帮我排查，把 GitHub 的**裸连**修好了。

回到发热本身。它不是「有点温」，是**能明显感觉到的那种烫**，而且有规律：**只要界面在动（流式输出中），就烫；静止放着，就凉下来。** 这个规律本身就是线索——发热跟着「渲染」走。

**有一点必须说清楚**：这个客户端**不是「WebView 套壳」**。它的外层是原生 Java 壳，里面内置 Node.js 运行时跑 DSH 引擎；但**界面层**是 DSH 自己的 Web 前端，最终由系统 **WebView** 渲染。所以本文后面所有关于 WebView 的结论，指的都是**界面渲染这一层**，不是整个 App 的架构。

> 📎 一个交叉验证：本文引用的采样 CSV 里，进程列名是 `eepseek.harness` —— 正好是包名 `com.deepseek.harness` 去掉首字母的截断。**这说明那份采样确实是针对这个客户端抓的。**

**「感觉烫」不是能拿来做决策的依据**，所以下一步是把它变成数字。否则整个项目就建立在「我觉得」上面。

## 2. 把「发热」变成数字

用采样工具对着那个第三方 Android 客户端跑一段真实的流式对话，得到 **123 行 × 36 列**的原始采样。

先看三个最直观的量级（A 组，123 行全量统计）：

| 指标 | 最小值 | 最大值 | **平均值** |
|---|---:|---:|---:|
| `CPU7(%)`（大核利用率） | 84.69% | 99.02% | **93.77%** |
| `CPU(℃)`（CPU 温度） | 88.80℃ | 98.10℃ | **94.52℃** |
| `Power(mW)`（整机功耗） | 4825 mW | 8828 mW | **6262 mW ≈ 6.3 W** |

这三行数字基本就说明了问题：

- **大核被长时间钉在 93% 以上。** 123 行里只有 **1 行**掉到 88% 以下，最低也有 84.69%。也就是说整段采样**没有一次真正的「空闲」**。
- **CPU 温度稳定在 94.5℃ 量级。** 全程区间 88.80 ~ 98.10℃，始终贴着 95℃ 上下。
- **整机功耗 6.3 W。** 对手机来说这是相当高的持续功耗（快充时也就 20 W 上下，日常待机通常不到 1 W）。

作为对照，整机 8 核的平均利用率 `CPU(%)` 只有 **46.22%**。这个对比很有意思：

> **8 个核里只有不到一半在忙，但大核已经被压到 94% 了。**

这说明负载不是「平均分摊」，而是**高度集中在少数核心上**——这正是「烫」的来源。热量集中在一点，散热来不及带走。

> 📎 顺带一个自洽性验证：`CPU(%)` 这一列是不是 8 核均值？抽查前 5 行，`CPU(%)` 与 `CPU0(%)` ~ `CPU7(%)` 的算术平均值误差都在 0.3 以内。**是均值。** 所以上面那句「不到一半在忙」是站得住的。

## 3. 定位到进程：热量是谁产生的

有了整机数据，下一个问题是：**这些 CPU 时间是谁花的？**

采样文件里带了三个进程级列，直接给出了答案（A 组，123 行全量）：

| 进程 / 线程 | 平均值 | 最大值 | 换算成「占单核」 |
|---|---:|---:|---:|
| `eepseek.harness(%)`（DSH 主进程） | 10.66% | 13.90% | 85.3% ~ 111.2% |
| `VizWebView(%)`（WebView 沙箱渲染进程） | 5.02% | 7.90% | 40.1% ~ 63.2% |
| `RenderThread(%)`（系统级渲染线程合计） | 13.80% | 20.90% | 110.4% ~ 167.2% |

**换算口径说明**：这三个列的值是「占整机 8 核的百分比」，所以「占单核的百分比」= 列值 × 8。（依据是上一条：整机列 `CPU(%)` 已验证为 8 核均值，同文件的进程列与之同口径。）

结论很清楚：

> **DSH 自己那个 App 进程（`eepseek.harness`）只占 0.85 核左右，但它的 WebView 渲染进程（`VizWebView`）单独再吃掉 0.40 核，而全系统的渲染线程合计吃掉 1.10 核。**

也就是说：**「渲染」这件事本身，就是这台手机上最重的一块计算负载。** 而 DSH 的界面渲染，几乎全部由 WebView 承担。

### 3.1 关于「WebView ≈ DSH 负载的 85%」这个说法

这个 85% 在传播过程中容易读错，需要把分母说清楚。

- **分母是「DSH 自身的 CPU 时间」**（也就是 `eepseek.harness` + `VizWebView`），不是整机。在这个口径下，WebView 渲染进程占 DSH 自身负载的绝大部分。
- **如果换成整机口径**，WebView 相关的计算大约占整机 CPU 时间的 **40%** 上下，对应到 README [第 7.1 节](../README.md#71-渲染不是手机发热的唯一原因甚至不是主要原因) 那张发热来源表里的 **「SoC 计算」** 那一格。

**换口径这件事很重要**：85% 听起来像「WebView 是唯一元凶」，但整机口径下它只有 40%——剩下 60% 是屏幕背光、射频、系统服务、其他后台进程。**这正是本项目最终只能承诺「1~3℃ 量级」而不是「从烫手变冰凉」的原因。**

## 4. 最隐蔽的发现：悬浮窗让 WebView 永不后台节流

前三节说明的是「WebView 渲染很重」。但真正让我意外的是下一步。

### 4.1 现象

正常情况下，一个 App 退到后台，系统会给它降优先级、限制 CPU、冻结渲染。这是 Android 的省电机制。

但 DSH 方案里有一个悬浮窗（小窗 / 悬浮球一类的常驻 UI）。**悬浮窗的存在，让 WebView 的渲染进程一直被认为「可见」，于是永远拿不到后台节流。**

### 4.2 实验 B 的数据

把悬浮窗开 / 关做成唯一的对照变量：

| 状态 | WebView 渲染进程 CPU | 说明 |
|---|---:|---|
| **悬浮窗开启**（App 退到后台） | **108.45%**（单核口径） | 完全没被节流，甚至超过一个核 |
| **悬浮窗关闭**（App 退到后台） | **0.95%**（单核口径） | 正常被节流，几乎归零 |

差距是 **两个数量级**。

### 4.3 结温的变化

对应地，CPU 结温出现约 **−30℃** 的落差。

> ⚠️ **口径提醒**：这个 −30℃ 是**实验 B** 里「悬浮窗开 / 关」两个状态之间的温差，**不是**实验 A 那份 123 行采样里的落差。实验 A 全程都在高负载，`CPU(℃)` 始终在 88.80 ~ 98.10℃ 之间，**不存在 30℃ 的落差**。两份数据不要混读。

### 4.4 为什么这一条最关键

因为它改变了对问题的定性。

- 如果问题只是「WebView 渲染重」→ 解法是「换一个轻的渲染方式」，也就是**用原生 UI 重写**。
- 但如果问题还包括「**后台还在满速渲染**」→ 那么哪怕前台优化得再好，**只要用户不彻底杀掉 App，它就会一直在后台烧电、一直热。**

**「50ms 批处理」这个优化目标的直接来源，就是这一条。** 既然渲染停不下来，那就至少让每一次渲染做更少的事。

## 5. 一个被推翻的估算（留在这里当警示）

排查过程中，我一度试图估算「用原生重写能省下多少工作量」，算出了一个 **约 11.6 人月** 的数字，并差点把它写进项目文档。

**后来这个估算被推翻了。** 原因很朴素：

- 它是**估算**，不是**实测**。分母（总工作量）本身就是我拍脑袋定的。
- 它把「AI 生成代码」和「人写代码」按同一个工时口径折算，这个折算本身没有依据。
- 更根本的是：**这个数字对判断「值不值得做」没有帮助。** 项目真正的价值在「批处理能把重绘降低多少」，而不在「省了多少人月」。

**所以本文不引用这个数字，README 里也没有它。** 把它记在这里，是因为「一个看起来很专业、其实是拍出来的数字，差点被当成结论写进文档」这件事本身值得留一笔。

## 7. 边界

写这份材料时，有几条边界必须划清楚，否则它会被误读：

1. **这是「立项背景」，不是「开发记录」。** 本文的结论是「问题在哪、有多大」，不是「代码怎么写」。代码在 [`README.md`](../README.md)，实现全部由 AI 完成。
2. **A 组数据只在单台设备上采过。** 测试设备：小米（型号 24117RK2CC）/ Android 16 / 骁龙 8 系平台（pm8550）。不同 SoC、不同调度策略下，渲染负载的占比会变。**不能外推。**
3. **85% 和 40% 是两个口径，不要混用。** 见 3.1 节。
4. **−30℃ 是悬浮窗实验的温差，不是 123 行采样里的落差。** 见 4.3 节。
5. **B、C 两组缺原始文件。** 见第 6 节。
6. **本文的数据来源是「我当时的实测」，不是「可发表的实验」。** 采样次数、环境控制、重复轮次都达不到严肃实验的标准。它足以支撑一个个人项目的方向判断，**不足以支撑任何工程结论**。
